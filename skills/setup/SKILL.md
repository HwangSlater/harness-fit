# harness-fit

Scripts live in `${CLAUDE_PLUGIN_ROOT}/scripts`. They print compact JSON; do not read the catalog files yourself (that is what keeps this cheap). Keep `--in-plugin` on every `apply.mjs` / `picker.mjs` command: it tells them the plugin is on in this session (this skill exists only then), so the hooks will run. Answer the user in their language (`selection.lang` in the result, else the language they write in). Keep the final report short.

## Arguments: $ARGUMENTS

### undo
Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply.mjs" . --undo` and report what was `removed` / `restored`. `trimmed`: files the user edited after setup — only the parts harness-fit added were taken out (CLAUDE.md block, the .gitignore line, the plugin entries in .claude/settings.json), the user's edits stay. `saved`: edited after setup — the edited copy was saved under `savedIn` and the file was still reverted (so hooks really stop); tell them where the copy is. `skipped`: backup entries that harness-fit never writes or that point outside the project (ignored — mention it, it may be a tampered backup). `kept`: the git pre-commit hook was replaced or edited after setup (`pre-commit install`, Husky, lines added by hand …) — harness-fit only touches a hook that is exactly its own launcher — so it was left in place to keep the team's checks running; `.git/hooks/pre-commit.legacy` in the list is harness-fit's old launcher that the pre-commit framework moved there — it does nothing once setup is undone, and the user may delete it; `.pre-commit-config.yaml` in the list means the `id: harness-fit` entry the user pasted is still there — it now only prints that the runner is missing and lets commits through, and the user may remove that entry (harness-fit never edits that file); `CLAUDE.md` in the list means its harness-fit block markers no longer pair up, so it was left as is — the user deletes the block by hand. `saved` also covers a folder the user created after setup at a path setup had deleted (a skill folder with the same name): it is saved under `savedIn` before harness-fit's copy is put back. `notes` with `reason: "legacy-not-restored"`: setup had deleted harness-fit's old launcher from `.git/hooks/pre-commit.legacy` and undo did not put it back on purpose — the pre-commit framework runs that file on every commit, and on Windows it fails (`/bin/sh` not found) and blocks every commit; nothing is lost, say it in one line. `{"error":"no-backup"}` means there is nothing to undo. `github` (if setup changed GitHub repository settings): `restored` were set back; `edited` were changed again on GitHub after setup, so they were left alone; `failed` could not be set back — tell the user each one with the value to set it back to (`to`) in the repository settings; `error: "repo-mismatch"` means origin now points to a different repository, so nothing on GitHub was touched. If undo says `no-backup` but the user wants harness-fit gone (another PC, a fresh clone, or more than the last setup), offer `remove` below.

### remove (the project is ending: take out everything harness-fit added)
Unlike undo, this needs no backup and covers every earlier setup. It only removes what is provably harness-fit's. Always run the dry run first: `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply.mjs" . --remove --dry-run`. Show `removed` (whole files and folders) and `trimmed` (only harness-fit's part is taken out: the CLAUDE.md block, the two plugin entries in `.claude/settings.json`, the `.gitignore` line; the rest of the file stays) and `kept` as short lists. If `claudeMdLines` is there, say how many lines of CLAUDE.md go (the harness-fit block, marker lines included). Then ask once whether to go ahead, and wait for a reply that says yes. Then run the same command without `--dry-run` and report. Remove and undo work on the git top-level folder even when run from a subfolder; `folder` says which folder was used, and `git: false` means it is not a git repository, so the given folder was used as is. Say the folder in that case.
- `kept` reasons: `edited` — a skill folder changed after download (checked against the file hashes in its `.harness-source.json`); `unverifiable` — a skill downloaded before hashes were recorded, or whose name cannot be checked, so it cannot be told whether it is harness-fit's unchanged copy. Both are deleted only with `--force`: ask about them by name and add `--force` only if the user says to delete them anyway. `link` — a symbolic link or junction; harness-fit never follows a link out of the project, so the user deletes it by hand if they want (a kept `.claude/harness-backup` link also keeps its `.gitignore` line). `not-ours` — the file carries harness-fit's marker but is not exactly what harness-fit wrote (lines added by hand), or a skill folder whose name is not the skill id it was downloaded as (a copy the user made under another name), so it stays. `markers` — `CLAUDE.md`'s harness-fit block markers do not pair up (two start markers, no end marker, or the end before the start; markers quoted inside a sentence or a code block do not count), so the file was not touched; tell the user to delete the harness-fit block by hand (from `<!-- harness-fit:start -->` to `<!-- harness-fit:end -->`). `settings-broken` — `.claude/settings.json` is not valid JSON, so the plugin entries could not be taken out; the user fixes the file, then runs remove again.
- `manual` (harness-fit does not do these; say each in one line):
  - `plugin`: the plugin itself is still installed. Give `commands` if any (e.g. `claude plugin uninstall harness-fit@harness-fit --scope project`), otherwise `/plugin` → harness-fit → Uninstall. If `userScope` is true, it is installed for all of the user's projects; uninstalling at user scope removes it everywhere. With `.claude/harness.json` gone, its hooks do nothing in this project, so keeping it installed is harmless.
  - `teammates`: the plugin entries were taken out of `.claude/settings.json`. Once that change is committed and pushed, teammates are no longer asked to install the plugin. The deleted skill folders, `CLAUDE.md` and `.claude/harness.json` also need committing. Do not commit unless the user asks.
  - `pre-commit-entry`: delete the `id: harness-fit` entry from `.pre-commit-config.yaml` by hand. harness-fit never edits that file. Until then the entry only prints that its runner is missing and lets commits through.
  - `git-hook-line`: `file` is the user's own git hook (Husky, `core.hooksPath` or a hand-written `.git/hooks/pre-commit`) with a line that calls harness-fit's commit check; the user removes that line.
  - `github`: GitHub repository settings were changed by an earlier setup (`stamps`). Remove does not touch GitHub. The user changes them back in the repository settings. If that setup was the last one, run `undo` before `remove`; undo sets them back.
- The `.gitignore` line is taken out only if harness-fit added it (`.claude/harness.json` records it from this version on). If the line was already there before the first setup, it stays. Setups made by older versions did not record it, so the line is taken out.
- `{"error":"conflicting-modes"}`: two modes were given at once (e.g. `--remove --undo`); nothing ran. Run one of them.
- `{"error":"write-failed","mode":"remove"}`: it stopped half-way. Tell the user the `path` and `code` as for apply, and run the same remove again after fixing the cause; it removes what is left, and the backup folder goes last.

### First, for auto and default (not undo or remove): is there anything to recommend from?
Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/detect.mjs" . --brief`. If `thin` is false, go on without saying anything.
If `thin` is true (no file tells the stack — e.g. an empty or brand-new repo), do not open anything yet. Tell the user in 2–3 lines that a tailored recommendation is not possible because the repo has nothing to read yet, so it would start from the default set and they pick by hand — and ask whether that is OK, or whether they want to say what they are building (language/framework, solo or team). Then wait for the answer.
- "OK" → continue as usual.
- They describe the project → map it to names in `knownStacks` (ignore anything not in the list) and add `--stack "<A>,<B>"`, plus `--team` if more than one person will work on it, to the `recommend.mjs` / `picker.mjs` command below. Say in one line what you passed.
- They decline → stop; nothing was changed.

### Then, for auto and default: do not add what the user already has
The scripts already leave out hooks that an existing hook (user or project settings, other plugins) blocks the same way — they test it with sample inputs — and skills with the same name. Two things need your judgment; do them once, silently unless something matches:
Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/overlap.mjs" . --lang <ko|en>`.
- `installed` vs `catalog`: if an installed skill clearly does the same job as a catalog skill (not just the same topic), add `--similar "<catalog id>=<installed name>,…"`.
- `rules`: harness-fit's CLAUDE.md lines, numbered per rule id (`when` = only added when that hook is on/off). Compare them with the user's own text only: the global `~/.claude/CLAUDE.md` and the project `CLAUDE.md` that are already in your context (do not read other files for this). If the result has `projectClaudeMd`, use it instead of the project `CLAUDE.md` in your context — it is that file without the `<!-- harness-fit:start -->`…`<!-- harness-fit:end -->` block, which is harness-fit's own earlier output, not the user's. Never count a line inside that block as already written. If the result has `userRules` (the user's own `.claude/rules/*.md` files, project and `~/.claude`), compare with those too; a rule with `paths` only applies to those files, so it covers a harness-fit line only when that line is about the same files. If a line already says the same thing in the user's own text, add `--skip "<rule id>:<n>,…"`.
- **Contradictions** (same user text as above; in a team repo — see below — only the project's own text, never `~/.claude` files): also look for a `rules` line or a `hooks` entry (`enforces`, `blocks` — the hooks that would be turned on; an entry with `flows` is only turned on with those branch strategies, so say so in the question) whose behaviour the user's text explicitly asks the opposite of — e.g. 「main 에 바로 커밋한다」 vs protect-branch or the GitHub Flow lines, "commit messages in English" vs a Korean `commit-msg` setting, "use `git add .`" vs git-add-all. Silence, a softer wording or a different topic is not a contradiction. Skip pairs in `knownConflicts` (same kind + id — for a rule, the same `hash`; its `line` is where that line is now in `rules` — and the same `userText`: already decided). `goneConflicts` are records whose user text changed or was deleted (or, in a team repo, that point at a `~/` file); they are dropped — if the new text still contradicts, ask again. `restored`: earlier "keep theirs" choices that were dropped, so that hook or line goes back to harness-fit's recommendation — say so in one line (e.g. "Your rule about committing to main is gone, so protect-branch is back on"). If there are contradictions, ask before running `recommend.mjs` or opening the picker: one short question per pair, all in one message — quote the user's line and say its file, say what harness-fit would add, and offer two choices: keep theirs (harness-fit leaves out that line or turns that hook off) or use harness-fit's (then they should edit their own line; you never edit it). Recommend neither. In a team repo add that the choice is saved in `.claude/harness.json` and applies to everyone. Wait for the answers, then pass them as `--conflicts '<JSON array>'` (or write the array to a temp file and pass its path when a quoted line contains `'`): `[{"kind":"hook","id":"protect-branch","choice":"mine","file":"~/.claude/CLAUDE.md","userText":"main 에 바로 커밋한다"},{"kind":"rule","id":"github-flow","line":2,"choice":"harness","file":"CLAUDE.md","userText":"…"}]` — `choice` `mine` = keep theirs, `harness` = use harness-fit's; `file` only one of `CLAUDE.md`, `.claude/rules/<…>.md`, `~/.claude/CLAUDE.md`, `~/.claude/rules/<…>.md` (no `~/` file in a team repo); `userText` copied exactly from that file, at least 8 characters. Saved choices carry over by themselves; pass only the new answers. `{"error":"bad-conflicts"}`: fix the entries listed in `why` and rerun; nothing ran.
- **Team repos:** if `detect --brief` showed more than one author (the setup is shared with teammates), compare only with what is in the project — the project `CLAUDE.md`, project `.claude/rules/`, and installed skills whose `scope` is `project`. Teammates do not have your global `~/.claude` files or user-scope skills, so those are not a reason to leave something out.
Pass these flags to `recommend.mjs` / `picker.mjs` below and say in one line what you left out and why (e.g. "Left out the code-simplification skill: refactor-check does the same"). When unsure, do not skip — the user can still turn things off in the picker.

### default: picker
1. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/picker.mjs" . --in-plugin --lang <ko|en>` (the language the user writes in) **in the background**. It opens the browser and prints the URL on stderr. In a project set up before, the picker starts from last time's choices (it says so and offers "reset to recommended"). Tell the user in one line that the picker is open (give the URL in case the browser did not open; if they cannot open it, suggest `/harness-fit:setup auto`). In that same message add the auto stack notes that apply (built-in `/claude-api`; for ROS 2 and Django the files from the `git ls-files` checks, and the `offer` paths from `detect --brief`, which they can add under 「파일 보호」 → 「더 지킬 파일·폴더」 in the picker's hook step) — one line each, nothing else.
2. Wait for the background task to finish — do not poll. Its stdout is one JSON object with `status`.
   - `cancelled` / `timeout`: say nothing was changed.
   - `applied`: report from the JSON —
     - combo and Git strategy (`labels.combo`, `labels.flow`),
     - what went in, grouped by kind so the user can tell them apart — one line each, with where it lives:
       skills actually installed (`labels.skills`; failed and manual ones are not in it) → `.claude/skills/`; hooks (`labels.hooks`) → `.claude/harness.json`, checked automatically before each command or file write; CLAUDE.md rules (`labels.rules` + the Git strategy) → the marked block in `CLAUDE.md`. Other files from `changed` (settings.json, .gitignore, request note) in one short line,
     - `failed`: skills that could not be downloaded, each with `error` (the reason — say it in one plain line per skill, or once if they share it). If `reason` is `"rate-limit"`, GitHub's rate limit was hit: say so plainly with `waitMin` (「GitHub 호출 한도에 걸렸어요 — 약 N분 뒤에 다시 받을 수 있어요」 / "GitHub rate limit — try again in about N min"; `retryAt` is the time) and do not retry before then; signing in with `gh auth login` raises the limit. Offer to retry only those: `node "${CLAUDE_PLUGIN_ROOT}/scripts/apply.mjs" . --in-plugin --retry <id,id>` (adds them to the same backup, so undo still goes back to before setup). Do not re-run the whole apply. In its result, `skipped` are skills whose folder already exists and was not created by this setup — they were left untouched; `unknown` are names that are not downloadable catalog skills (say so; check the spelling).
     - If an apply/undo/retry run prints `{"error":"write-failed"}`: tell the user which `path` could not be written and the `code` (EPERM/EACCES = no permission, ENOSPC = disk full, EBUSY = file locked by another program) in one plain sentence, and suggest fixing that before trying again. What happened depends on `mode`:
       - `apply`: nothing was changed — files written before the failure were put back automatically. **Never run `--undo` after this**: it would undo the user's previous setup instead.
       - `apply-partial`: files were changed and could not be put back automatically. After fixing the cause, run `--undo` once to return to before this setup.
       - `retry`: some skill folders may have been downloaded but not recorded; name `.claude/skills/<id>` for the ids you asked for and let the user decide whether to keep them. Run the same retry again after fixing the cause.
       - `undo`: it stopped half-way; after fixing the cause, run `--undo` again — it continues from where it stopped.
     - `{"error":"bad-selection"}`: the selection file could not be read or is not valid JSON — write it again and rerun; nothing was changed.
     - `workspace` (only when the folder is a workspace — not a git repo, with two or more repos directly inside; `detected.workspace` in recommend): one setup and CLAUDE.md at the top, the git pre-commit hook per repo.
